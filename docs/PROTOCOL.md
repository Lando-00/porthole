# porthole protocol

The porthole CLI extension and the porthole VS Code companion are two separate
processes that never share memory, a port, or a parent. Everything they know
about each other travels through files in known locations.

This document is the contract. Both halves implement against it, and
`tests/validate.mjs` asserts the parts that can be checked statically.

> **Why files?** The CLI can only push a URI at VS Code, which is
> fire-and-forget: spawning the launcher always "succeeds", so a window that
> never received the request looks exactly like one that acted on it. That is
> how porthole 0.3.0 could report a successful `/cops` while opening nothing.
> A file written back turns "did it work?" into a question with an answer.

## Locations at a glance

| Path | Written by | Read by | Purpose |
|---|---|---|---|
| `<tmp>/porthole/req/<requestId>.json` | CLI | companion | Request payload |
| `<tmp>/porthole/ack/<requestId>.json` | companion | CLI | Result of that request |
| `~/.copilot/porthole/outbox/<endpointId>/<messageId>.json` | companion | CLI | Editor → CLI message |
| `~/.copilot/porthole/outbox/<endpointId>/inflight/<messageId>.json` | CLI | CLI | Claimed, not yet delivered |
| `~/.copilot/porthole/outbox-ack/<messageId>.json` | CLI | companion | Delivery outcome |
| `~/.copilot/porthole/companion-<pid>.json` | companion | CLI | "A window is alive" |
| `~/.copilot/porthole/cli-<endpointId>.json` | CLI | companion | "A session is alive" |
| `<sessionDir>/porthole/reviews/<slug>.json` | companion | companion, CLI | Saved findings |

`<tmp>` is `os.tmpdir()`. `~/.copilot` is `$COPILOT_HOME` when set and it
exists, otherwise `~/.copilot`. `<sessionDir>` is
`~/.copilot/session-state/<sessionId>`.

### Why the outbox is not in the temp directory

`os.tmpdir()` is per-user on Windows, but on Linux and macOS `/tmp` is
world-writable and shared between local users.

That is tolerable for `req`/`ack`: the worst a hostile local user can do by
forging a request is make someone's editor reveal a line or draw an
annotation. Forging an *ack* is bounded by having to guess a
`<epochMillis>-<8 random hex>` id before the real companion answers, within the
timeout.

The outbox is categorically different. It injects a **prompt into an agent that
can run shell commands**, so it lives under the user-owned `~/.copilot`
directory on every platform. The CLI refuses to read an outbox directory it
does not own, and creates it with owner-only permissions (`0o700`).

> A deliberate non-goal: defending against a *same-user* process. Such a process
> can already edit the extension source, so a capability token in a file it can
> also read would be security theatre. The boundary here is the user account.

## Identifiers

- **`requestId`** — `<epochMillis>-<8 hex chars>`, generated by the CLI.
- **`messageId`** — same shape, generated by the companion.
- **`endpointId`** — 16 random hex chars, generated **once per CLI extension
  load**. This, not `sessionId`, is the transport address.
- **`sessionId`** — the Copilot CLI session UUID. Metadata for display, and
  may be `null` (see §2).

### Why `endpointId` and not `sessionId`

Two CLI processes can be attached to the same session id — a resumed session is
the common case. If the presence file and the outbox were keyed by `sessionId`,
those processes would overwrite each other's presence, poll the same outbox,
steal each other's messages, and delete each other's file on shutdown.

`endpointId` is unique per process, so none of that can happen. `sessionId` and
`sessionName` ride inside the file for display in the "which session?"
quick-pick.

### Path safety

Ids become filenames, so every reader **must** sanitise before use:

```js
String(value).replace(/[^\w.-]/g, "_").slice(0, 128)
```

Sanitising is lossy, so it is a backstop, not validation. Readers **also**
reject ids that do not match their documented shape, and resolve every
constructed path and confirm it is still inside the directory it should be in
before touching it. A caller that does neither can be walked out of its
directory with `../`.

## 1. CLI → companion (request/ack)

```
1. CLI writes   <tmp>/porthole/req/<requestId>.json     (omitted for payload-free routes)
2. CLI fires    <scheme>://lando-00.porthole-companion/<route>?req=<requestId>
3. companion reads and DELETES the payload
4. companion writes <tmp>/porthole/ack/<requestId>.json
5. CLI polls the ack every 10ms until companionTimeoutMs, then DELETES it
```

`<scheme>` is `vscode` or `vscode-insiders` and **must match the build the
companion runs in**, or the URI is delivered to the wrong editor and silently
goes nowhere. The CLI takes the scheme from the companion's heartbeat.

The URI authority is the **lower-cased** extension id.

### Ack shape

```jsonc
{
  "ok": true,
  "at": "2026-08-04T08:00:00.000Z",   // added by the companion on write
  "result": { },                       // route-specific data, see below
  "error": "...",                      // present when ok is false
  "reason": "absent|timeout|refused|error"  // set by the CLI, not the companion
}
```

`result` carries data flowing **back** to the CLI. Routes that only perform an
action omit it. Anything a tool needs to return to the model goes here, not in
`error`.

Acks are written to `<file>.tmp` and renamed, so a reader never sees a
half-written ack.

### `reason` values

Set by the CLI so callers can react without parsing English:

| `reason` | Meaning | Right response |
|---|---|---|
| `absent` | No live companion heartbeat | Tell the user to open VS Code; do **not** burn the timeout |
| `timeout` | Fired, no ack in time | Window busy or companion needs a reload |
| `refused` | Companion answered `ok: false` | Report the companion's own `error` |
| `error` | Could not spawn the launcher | Editor path problem |

### Routes

| Route | Payload | Returns `result` | Added |
|---|---|---|---|
| `reveal` | `{ file, startLine, endLine, ... }` | no | 0.1.0 |
| `clear` | none | no | 0.1.0 |
| `ping` | none | heartbeat fields | 0.2.0 |
| `annotate` | `{ title, clearExisting, annotations[] }` | no | 0.2.0 |
| `annotate-clear` | none | no | 0.2.0 |
| `symbol` | `{ file, symbol, ... }` | no | 0.2.0 |
| `diagnostics` | see below | **yes** | 0.3.0 |
| `tour` | see below | **yes** | 0.3.0 |
| `review-save` | `{ slug, title }` | **yes** | 0.3.0 |
| `review-list` | `{ limit, repo }` | **yes** | 0.3.0 |
| `review-load` | `{ file }` or `{ slug }` | **yes** | 0.3.0 |

An unknown route is answered with `ok: false` rather than ignored, so an old
companion paired with a new CLI reports a version mismatch instead of hanging
until the timeout.

**Route validity is checked before payload validity**, so an unknown route with
no payload blames the route, not the missing file.

> `review-list` and `review-load` are also implemented **directly in the CLI**,
> which reads the same files. Routing a pure filesystem scan through a URI, a
> window choice and a timeout adds failure modes without adding capability. The
> routes exist only for the companion's own palette commands.

#### `diagnostics`

```jsonc
// payload
{
  "scope": "open",          // "open" | "workspace" | "file", default "open"
  "file": "C:\\repo\\a.ts", // required when scope is "file"
  "severities": ["error", "warning"],  // default: error + warning
  "limit": 100              // max entries returned, default 100, hard cap 500
}

// result
{
  "files": [
    {
      "file": "C:\\repo\\src\\a.ts",
      "diagnostics": [
        {
          "severity": "error",       // error | warning | info | hint
          "startLine": 30,           // 1-based, inclusive
          "endLine": 30,
          "startCol": 5,
          "message": "Type 'X' is not assignable to 'Y'.",
          "source": "ts",            // may be absent
          "code": "2322"             // may be absent, string or number
        }
      ]
    }
  ],
  "counts": { "error": 3, "warning": 7, "info": 0, "hint": 0 },
  "annotations": 4,         // porthole's own entries, excluded from `files`
  "truncated": true,        // entries were dropped to honour `limit`
  "scanned": 42             // files considered
}
```

Entries whose `source` is `porthole` are **excluded**, so the agent never reads
its own annotations back as if they were findings. Messages are truncated to
1000 characters. Ordering is by severity, then file, then line, so truncation
drops the least important entries rather than an arbitrary tail.

#### `tour`

```jsonc
// payload
{
  "title": "how a request reaches the editor",
  "steps": [                 // 1-50 steps; beyond that the result is refused
    {
      "file": "src/companion.mjs",   // absolute, or relative to a workspace folder
      "startLine": 120,              // required, 1-based
      "endLine": 145,                // defaults to startLine
      "stepTitle": "the entry point",// short, shown in the CodeLens
      "narration": "...",            // longer prose, max 2000 chars
      "severity": "info"             // styling only
    }
  ],
  "start": true              // begin at step 1 immediately, default true
}

// result
{ "steps": 5, "skipped": [ { "index": 3, "reason": "file not found" } ] }
```

A step whose file cannot be resolved is **skipped and reported**, not silently
dropped — the same class of bug as the fire-and-forget URI.

#### `review-save` / `review-list` / `review-load`

```jsonc
// review-save payload / result
{ "slug": "launch-path-audit", "title": "Launch path audit" }
{ "file": "C:\\...\\reviews\\launch-path-audit.json", "findings": 9 }

// review-list result
{ "reviews": [ { "slug", "title", "file", "createdAt", "sessionId", "repo", "findings": 9 } ] }

// review-load result
{ "review": { /* §4 */ }, "resolution": { "resolved": 7, "shifted": 1, "changed": 1, "missing": 0 } }
```

## 2. Presence

Neither side can enumerate the other's processes, so both drop a heartbeat and
prune entries whose pid is dead. This is what makes "nothing is listening"
answerable in about a millisecond instead of a full timeout.

### Companion → `~/.copilot/porthole/companion-<pid>.json`

```jsonc
{
  "pid": 12345,
  "version": "0.3.0",
  "uriScheme": "vscode-insiders",
  "appName": "Visual Studio Code - Insiders",
  "appHost": "desktop",          // "desktop" | "web" | remote host kind
  "remoteName": null,            // "wsl" | "ssh-remote" | "dev-container" | null
  "tmpdir": "C:\\Users\\me\\AppData\\Local\\Temp",
  "copilotHome": "C:\\Users\\me\\.copilot",
  "hostSqlite": true,
  "workspaceFolders": ["C:\\repo", "C:\\Users\\me\\.copilot\\session-state\\<id>"],
  "updatedAt": "2026-08-04T08:00:00.000Z"
}
```

Written on activate and refreshed on window-state and workspace-folder changes
— not on a timer, so an idle window costs nothing. Deleted on deactivate.

### CLI → `~/.copilot/porthole/cli-<endpointId>.json`  *(new in 0.5.0)*

```jsonc
{
  "endpointId": "9f2c41ab77e05d3e",
  "sessionId": "eeb847a2-2d90-4cc6-a64f-c312bdb8f8af",  // may be null
  "sessionName": "Build Copilot CLI Plugin",             // may be null
  "pid": 6789,
  "cwd": "C:\\repo",
  "projectRoot": "C:\\repo",
  "tmpdir": "C:\\Users\\me\\AppData\\Local\\Temp",
  "version": "0.5.0",
  "startedAt": "2026-08-04T08:00:00.000Z",
  "updatedAt": "2026-08-04T08:00:00.000Z"
}
```

Written on load, refreshed on each command, deleted on unload.

> **Identity caveat.** `ctx.sessionId` is only available inside a command
> handler. At load the extension tries the basename of `session.workspacePath`.
> If that is unavailable, the presence file is still written — with
> `sessionId: null` — because the address is `endpointId`, which is always
> known. `sessionId` and `sessionName` are filled in as soon as a command
> reveals them.
>
> This is why the reverse channel is keyed on `endpointId`: it works from the
> first moment the extension loads, whether or not a porthole command has ever
> run. The quick-pick falls back to `cwd` when there is no session name yet.

### Liveness

A reader treats an entry as live only if `process.kill(pid, 0)` succeeds, and
deletes the file otherwise. A crashed process cannot leave a lie behind.

### Remote and cross-filesystem pairings

The two halves only meet on a shared filesystem. When VS Code runs in WSL, a
container, over SSH, or in the browser, the extension host's `os.tmpdir()` and
home directory are **not** the CLI's, and every request would time out with no
explanation.

Both presence files therefore publish `tmpdir` and `copilotHome`. Before
pairing, each side compares them; a mismatch, or a non-null `remoteName` paired
with a local CLI, is reported immediately as an unsupported pairing:

> porthole: this VS Code window is running in WSL, so it cannot see the CLI's
> temp directory. Run the CLI inside the same environment.

Detecting this is the whole point — a clear refusal beats a silent timeout.

## 3. Companion → CLI (the reverse channel)  *(new in 0.5.0)*

```
1. companion resolves the target endpoint from cli-<endpointId>.json
2. companion writes  outbox/<endpointId>/<messageId>.json.tmp  then RENAMES it
3. CLI polls its own outbox, and CLAIMS a message by renaming it into
   outbox/<endpointId>/inflight/<messageId>.json
4. CLI awaits session.send({ prompt, mode })
5. CLI writes outbox-ack/<messageId>.json, then deletes the inflight file
6. companion polls for the ack and reports the outcome
```

Only the outbox for **its own** `endpointId` is polled, and `endpointId` is
unique per process, so two CLI processes cannot take each other's messages —
including two processes attached to the same resumed session.

### Atomicity and delivery semantics

Every write in this flow is **write-to-`.tmp`-then-rename**, so no reader ever
parses a half-written file. Readers ignore `.tmp` files entirely.

Claiming is a **rename**, which is atomic on both Windows and POSIX. A rename
that fails because the file is gone means another poll already claimed it, and
is not an error.

Delivery is **at-most-once**, deliberately:

> A message is claimed before it is sent, so a crash between claim and send
> loses it. The alternative — send first, delete after — can deliver the same
> prompt twice if the process dies in between. A duplicated prompt to an agent
> that can run shell commands is worse than a send the user can see failed, and
> the ack makes the failure visible.

A message left in `inflight/` past the TTL is **not retried**. It is swept, and
acked as `unconfirmed` so the editor can tell the user it may or may not have
arrived.

### Message shape

```jsonc
{
  "messageId": "1785615001442-a1b2c3d4",
  "endpointId": "9f2c41ab77e05d3e",
  "sentAt": "2026-08-04T08:00:00.000Z",
  "source": "vscode",
  "kind": "selection",
  "note": "why does this branch never fire?",
  "file": "C:\\repo\\src\\editor.mjs",
  "language": "javascript",
  "startLine": 25,
  "endLine": 41,
  "selection": "function launcherFor(name) { ... }",
  "diagnostics": [
    { "severity": "error", "line": 30, "message": "...", "source": "ts" }
  ]
}
```

### Delivery

`session.send({ prompt, mode: "enqueue" })`, **awaited**, so the ack reflects
what actually happened rather than what was attempted. Enqueue is the default
so a message never interrupts a turn already in flight.

> The SDK forbids calling `session.send()` synchronously from
> `onUserPromptSubmitted`. porthole sends from a timer, which is safe.

### Outbox ack shape

```jsonc
{
  "messageId": "...",
  "status": "accepted",   // see below
  "at": "2026-08-04T08:00:00.000Z",
  "error": "..."          // present unless accepted
}
```

| `status` | Meaning | What the editor shows |
|---|---|---|
| `accepted` | `session.send()` resolved | "Sent to Copilot" |
| `rejected` | Malformed, or failed validation | The reason, as an error |
| `rate-limited` | Too many messages this minute | "Slow down" — try again |
| `expired` | Older than the TTL when found | "Not delivered" |
| `unconfirmed` | Claimed, outcome unknown after a crash | "May or may not have arrived" |

**Every consumed message gets an ack**, including rejected, rate-limited and
expired ones. A dropped message that is only written to a log the user never
reads is exactly the silent failure this project already shipped once.

If no ack appears within the companion's wait, the editor says *not confirmed*
— never "sent".

### Safety rules — all mandatory

Editor content becomes an agent prompt, so it is **untrusted input**:

1. The selection is wrapped in a fenced block and labelled as editor-provided
   content that must not be treated as instructions. This is **context for the
   model, not a security boundary** — the real boundary is rule 6.
2. Messages are size-capped (32 KB total, 16 KB of selection); oversized
   selections are truncated with a visible marker.
3. Delivery is rate-limited to 10 messages per minute; excess is acked
   `rate-limited`, not silently dropped.
4. A message is only produced by an explicit user command in the editor. The
   CLI cannot verify this, which is why it does not depend on it.
5. Each `messageId` is delivered at most once, enforced by the atomic claim
   rename rather than by an in-memory set that a restart would forget.
6. The outbox lives under the user-owned `~/.copilot` with `0o700`
   permissions, and the CLI refuses to read it if it is not owned by the
   current user. **This is what actually stops another local user injecting a
   prompt.**
7. Files older than the TTL are acked `expired` and deleted, so a crash cannot
   replay a stale message hours later.

## 4. Reviews  *(new in 0.5.0)*

A review is a saved set of findings: the annotations or tour steps present when
it was saved, plus enough context to make sense of them later.

**Location:** `<sessionDir>/porthole/reviews/<slug>.json`

```jsonc
{
  "schema": 1,
  "slug": "launch-path-audit",
  "title": "Launch path audit",
  "createdAt": "2026-08-04T08:00:00.000Z",
  "sessionId": "eeb847a2-...",
  "repo": "C:\\repo",
  "branch": "main",
  "commit": "4744ab9",
  "dirty": false,                 // was the tree modified when saved
  "findings": [
    {
      "file": "src/editor.mjs",   // relative to repo when inside it
      "startLine": 25,
      "endLine": 41,
      "severity": "warn",
      "stepTitle": "display name vs slug",
      "message": "...",
      "narration": "...",
      "anchor": {
        "sha256": "3f9a...",      // hash of the exact range text when saved
        "firstLine": "function launcherFor(name) {",
        "lastLine": "}"
      }
    }
  ]
}
```

`file` is stored **relative to `repo`** when the file lives inside it, so a
review still resolves after the repository is moved or cloned elsewhere.

### Stale findings

A review outlives the code it describes. Line numbers alone are not enough:
after an edit, `startLine: 25` may point at something completely unrelated, and
presenting a finding on innocent code is the worst thing a review tool can do.

Every finding therefore carries an **anchor**: a hash of the exact text of its
range, plus its first and last line. On load, each finding is resolved:

| Status | Test | Behaviour |
|---|---|---|
| `resolved` | Text at the stored range still hashes to `anchor.sha256` | Show as saved |
| `shifted` | Not at the stored range, but the same text is found within ±200 lines | Re-point to the new range and say so |
| `changed` | File exists, anchor found nowhere | Show at the stored range, **clearly marked stale** |
| `missing` | File no longer exists | List it, do not open it |

`review-load` returns these counts in `result.resolution` so the agent can say
"7 of 9 findings still apply" rather than pretending all nine do.

### Containment

`review-load` accepts a path from outside, which would otherwise make it an
arbitrary JSON file reader. The resolved absolute path **must** sit under
`~/.copilot/session-state/*/porthole/reviews/`, and the `slug` must match
`^[\w-]{1,64}$`. Anything else is refused.

### Cross-session loading

Reviews live in the session folder that created them, but a later session must
be able to load them. Readers therefore scan:

```
~/.copilot/session-state/*/porthole/reviews/*.json
```

newest first, rather than looking only in the current session. Listing may
filter by `repo` so an unrelated project's reviews do not appear.

Because this is a plain filesystem scan, **the CLI does it directly** and does
not need a running companion to list or load a review. Only saving needs the
editor, because only the editor knows the current annotation state.

### Todos

porthole **never writes to `session.db`**. `review-load` returns findings, the
agent discusses them with the user, and the agent creates todos with its own
tooling. This keeps porthole uncoupled from a schema it does not own.

## 5. Housekeeping

| Directory | Retention |
|---|---|
| `req/`, `ack/` | Swept after 1 hour; each file is deleted by its reader |
| `outbox/` | Unclaimed messages acked `expired` and deleted after 10 minutes |
| `outbox/*/inflight/` | Acked `unconfirmed` and deleted after 10 minutes |
| `outbox-ack/` | Swept after 1 hour |
| `~/.copilot/porthole/*.json` | Deleted on clean shutdown; pruned on dead pid |
| reviews | Kept indefinitely — user data |

Sweeps race between windows and sessions by design; every removal tolerates
`ENOENT`.

> **Only the owning CLI process sweeps its own outbox.** A shared sweep could
> delete a message between another process writing it and that process's next
> poll — a message lost with nobody to ack it. Companions never sweep an outbox
> they do not own; they only sweep `outbox-ack` entries for messages they sent.

## 6. Compatibility

The two halves version independently and users will run mismatched pairs.

- An **older companion** answers a new route with `unknown route '<x>'`. The
  CLI reports that the companion needs updating.
- An **older CLI** simply never calls the new routes.
- Payload fields are additive; unknown fields are ignored, never rejected.
- `schema` on the review file is the one hard version gate, because reviews
  outlive both halves.
