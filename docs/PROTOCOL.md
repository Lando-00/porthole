# porthole protocol

The porthole CLI extension and the porthole VS Code companion are two separate
processes that never share memory, a port, or a parent. Everything they know
about each other travels through files in known locations.

This document is the contract. Both halves implement against it, and
`tests/validate.mjs` asserts the parts that can be checked statically.

> **Why files?** The CLI can only push a URI at VS Code, which is
> fire-and-forget: spawning the launcher always "succeeds", so a window that
> never received the request looks exactly like one that acted on it. That is
> how porthole 0.3.0 could report a successful `/cops` while opening nothing.
> A file written back turns "did it work?" into a question with an answer.

## Locations at a glance

| Path | Written by | Read by | Purpose |
|---|---|---|---|
| `<tmp>/porthole/req/<requestId>.json` | CLI | companion | Request payload |
| `<tmp>/porthole/ack/<requestId>.json` | companion | CLI | Result of that request |
| `<tmp>/porthole/outbox/<sessionId>/<messageId>.json` | companion | CLI | Editor → CLI message |
| `<tmp>/porthole/outbox-ack/<messageId>.json` | CLI | companion | Delivery confirmation |
| `~/.copilot/porthole/companion-<pid>.json` | companion | CLI | "A window is alive" |
| `~/.copilot/porthole/cli-<sessionId>.json` | CLI | companion | "A session is alive" |
| `<sessionDir>/porthole/reviews/<slug>.json` | companion | companion, CLI | Saved findings |

`<tmp>` is `os.tmpdir()`. `~/.copilot` is `$COPILOT_HOME` when set and it
exists, otherwise `~/.copilot`. `<sessionDir>` is
`~/.copilot/session-state/<sessionId>`.

## Identifiers

- **`requestId`** — `<epochMillis>-<8 hex chars>`, generated by the CLI.
- **`messageId`** — same shape, generated by the companion.
- **`sessionId`** — the Copilot CLI session UUID.

Both ids become filenames, so every reader **must** sanitise before use:

```js
String(value).replace(/[^\w.-]/g, "_").slice(0, 128)
```

A caller that skips this can address any file on disk with `../`.

## 1. CLI → companion (request/ack)

```
1. CLI writes   <tmp>/porthole/req/<requestId>.json     (omitted for payload-free routes)
2. CLI fires    <scheme>://lando-00.porthole-companion/<route>?req=<requestId>
3. companion reads and DELETES the payload
4. companion writes <tmp>/porthole/ack/<requestId>.json
5. CLI polls the ack every 10ms until companionTimeoutMs, then DELETES it
```

`<scheme>` is `vscode` or `vscode-insiders` and **must match the build the
companion runs in**, or the URI is delivered to the wrong editor and silently
goes nowhere. The CLI takes the scheme from the companion's heartbeat.

The URI authority is the **lower-cased** extension id.

### Ack shape

```jsonc
{
  "ok": true,
  "at": "2026-08-04T08:00:00.000Z",   // added by the companion on write
  "result": { },                       // route-specific data, see below
  "error": "...",                      // present when ok is false
  "reason": "absent|timeout|refused|error"  // set by the CLI, not the companion
}
```

`result` carries data flowing **back** to the CLI. Routes that only perform an
action omit it. Anything a tool needs to return to the model goes here, not in
`error`.

Acks are written to `<file>.tmp` and renamed, so a reader never sees a
half-written ack.

### `reason` values

Set by the CLI so callers can react without parsing English:

| `reason` | Meaning | Right response |
|---|---|---|
| `absent` | No live companion heartbeat | Tell the user to open VS Code; do **not** burn the timeout |
| `timeout` | Fired, no ack in time | Window busy or companion needs a reload |
| `refused` | Companion answered `ok: false` | Report the companion's own `error` |
| `error` | Could not spawn the launcher | Editor path problem |

### Routes

| Route | Payload | Returns `result` | Added |
|---|---|---|---|
| `reveal` | `{ file, startLine, endLine, ... }` | no | 0.1.0 |
| `clear` | none | no | 0.1.0 |
| `ping` | none | heartbeat fields | 0.2.0 |
| `annotate` | `{ title, clearExisting, annotations[] }` | no | 0.2.0 |
| `annotate-clear` | none | no | 0.2.0 |
| `symbol` | `{ file, symbol, ... }` | no | 0.2.0 |
| `diagnostics` | `{ scope, severities, limit }` | **yes** | 0.3.0 |
| `tour` | `{ title, steps[] }` | no | 0.3.0 |
| `review-save` | `{ slug, title }` | **yes** (`{ file }`) | 0.3.0 |
| `review-list` | `{ limit }` | **yes** (`{ reviews[] }`) | 0.3.0 |
| `review-load` | `{ file }` or `{ slug }` | **yes** (`{ review }`) | 0.3.0 |

An unknown route is answered with `ok: false` rather than ignored, so an old
companion paired with a new CLI reports a version mismatch instead of hanging
until the timeout.

**Route validity is checked before payload validity**, so an unknown route with
no payload blames the route, not the missing file.

## 2. Presence

Neither side can enumerate the other's processes, so both drop a heartbeat and
prune entries whose pid is dead. This is what makes "nothing is listening"
answerable in about a millisecond instead of a full timeout.

### Companion → `~/.copilot/porthole/companion-<pid>.json`

```jsonc
{
  "pid": 12345,
  "version": "0.3.0",
  "uriScheme": "vscode-insiders",
  "appName": "Visual Studio Code - Insiders",
  "appHost": "desktop",
  "hostSqlite": true,
  "workspaceFolders": ["C:\\repo", "C:\\Users\\me\\.copilot\\session-state\\<id>"],
  "updatedAt": "2026-08-04T08:00:00.000Z"
}
```

Written on activate and refreshed on window-state and workspace-folder changes
— not on a timer, so an idle window costs nothing. Deleted on deactivate.

### CLI → `~/.copilot/porthole/cli-<sessionId>.json`  *(new in 0.5.0)*

```jsonc
{
  "sessionId": "eeb847a2-2d90-4cc6-a64f-c312bdb8f8af",
  "pid": 6789,
  "cwd": "C:\\repo",
  "projectRoot": "C:\\repo",
  "sessionName": "Build Copilot CLI Plugin",
  "version": "0.5.0",
  "startedAt": "2026-08-04T08:00:00.000Z",
  "updatedAt": "2026-08-04T08:00:00.000Z"
}
```

Written on load, refreshed on each command, deleted on unload.

> **Identity caveat.** `ctx.sessionId` is only available inside a command
> handler. At load time the extension derives its id from the basename of
> `session.workspacePath`. If that is unavailable, the presence file is written
> on the first command invocation instead — so a session that has run no
> porthole command may not be addressable yet.

### Liveness

A reader treats an entry as live only if `process.kill(pid, 0)` succeeds, and
deletes the file otherwise. A crashed process cannot leave a lie behind.

## 3. Companion → CLI (the reverse channel)  *(new in 0.5.0)*

```
1. companion resolves the target session from cli-<sessionId>.json
2. companion writes <tmp>/porthole/outbox/<sessionId>/<messageId>.json
3. CLI polls its own outbox directory, consumes and DELETES the file
4. CLI calls session.send({ prompt, mode })
5. CLI writes <tmp>/porthole/outbox-ack/<messageId>.json
6. companion polls briefly and reports delivered / not delivered
```

Only the outbox for **its own** `sessionId` is polled, so two live sessions
never steal each other's messages.

### Message shape

```jsonc
{
  "messageId": "1785615001442-a1b2c3d4",
  "sessionId": "eeb847a2-...",
  "sentAt": "2026-08-04T08:00:00.000Z",
  "source": "vscode",
  "kind": "selection",
  "note": "why does this branch never fire?",
  "file": "C:\\repo\\src\\editor.mjs",
  "language": "javascript",
  "startLine": 25,
  "endLine": 41,
  "selection": "function launcherFor(name) { ... }",
  "diagnostics": [
    { "severity": "error", "line": 30, "message": "...", "source": "ts" }
  ]
}
```

### Delivery

`session.send({ prompt, mode: "enqueue" })`. Enqueue is the default so a
message never interrupts a turn already in flight.

> The SDK forbids calling `session.send()` synchronously from
> `onUserPromptSubmitted`. porthole sends from a timer, which is safe.

### Safety rules — all mandatory

Editor content becomes an agent prompt, so it is **untrusted input**:

1. The selection is wrapped in a fenced block and labelled as editor-provided
   content that must not be treated as instructions.
2. Messages are size-capped; oversized selections are truncated with a marker.
3. Delivery is rate-limited per minute; excess messages are dropped and logged.
4. A message is only produced by an explicit user command in the editor.
5. Each `messageId` is delivered **once**; ids are remembered for the session.
6. Files older than the TTL are ignored and deleted, so a crash cannot replay
   a stale message later.

### Outbox ack shape

```jsonc
{ "messageId": "...", "ok": true, "at": "...", "error": "..." }
```

## 4. Reviews  *(new in 0.5.0)*

A review is a saved set of findings: the annotations or tour steps present when
it was saved, plus enough context to make sense of them later.

**Location:** `<sessionDir>/porthole/reviews/<slug>.json`

```jsonc
{
  "schema": 1,
  "slug": "launch-path-audit",
  "title": "Launch path audit",
  "createdAt": "2026-08-04T08:00:00.000Z",
  "sessionId": "eeb847a2-...",
  "repo": "C:\\repo",
  "branch": "main",
  "commit": "4744ab9",
  "findings": [
    {
      "file": "src/editor.mjs",     // relative to repo when inside it
      "startLine": 25,
      "endLine": 41,
      "severity": "warn",
      "stepTitle": "display name vs slug",
      "message": "...",
      "narration": "..."
    }
  ]
}
```

`file` is stored **relative to `repo`** when the file lives inside it, so a
review still resolves after the repository is moved or cloned elsewhere.

### Cross-session loading

Reviews live in the session folder that created them, but a later session must
be able to load them. Readers therefore scan:

```
~/.copilot/session-state/*/porthole/reviews/*.json
```

newest first, rather than looking only in the current session. Listing may
filter by `repo` so an unrelated project's reviews do not appear.

### Todos

porthole **never writes to `session.db`**. `review-load` returns findings, the
agent discusses them with the user, and the agent creates todos with its own
tooling. This keeps porthole uncoupled from a schema it does not own.

## 5. Housekeeping

| Directory | Retention |
|---|---|
| `req/`, `ack/` | Swept after 1 hour; each file is deleted by its reader |
| `outbox/`, `outbox-ack/` | Swept after 1 hour; ignored if older than the TTL |
| `~/.copilot/porthole/*.json` | Deleted on clean shutdown; pruned on dead pid |
| reviews | Kept indefinitely — user data |

Sweeps race between windows and sessions by design; every removal tolerates
`ENOENT`.

## 6. Compatibility

The two halves version independently and users will run mismatched pairs.

- An **older companion** answers a new route with `unknown route '<x>'`. The
  CLI reports that the companion needs updating.
- An **older CLI** simply never calls the new routes.
- Payload fields are additive; unknown fields are ignored, never rejected.
- `schema` on the review file is the one hard version gate, because reviews
  outlive both halves.
